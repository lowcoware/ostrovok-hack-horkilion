## Context

Фаза 0 закрыла контракты: внешнее API, `TripPlan` v2, proto v2 поставщиков, моки фронта, CI-проверки (PR #1). Фаза 1 по roadmap должна провести запрос «хочу к тёплому морю в ноябре, недорого, с ребёнком, без долгих перелётов» до оплаченной корзины с транспортом, отелем и трансфером на сервере.

С момента roadmap изменились две вещи:

1. **Состав команды.** Не два бэкендера и фронтендер, а три роли: бэкенд (BE), данные (DS) и фронт (FE). Треки A и B из roadmap сливаются в роль BE; сбор и подготовка данных выделены в отдельную роль DS.
2. **Объём по визам.** ADR 0003: подбор по всем странам с пометкой визы, виза по гражданству, выбор гражданства и города отправления.

Эта спека делит фазу 1 на задачи по ролям и фиксирует, как результаты разных людей стыкуются.

## Цель фазы

Фаза закрыта, когда на задеплоенном сервере выполняется всё ниже:

1. Запрос «хочу к тёплому морю в ноябре, недорого, с ребёнком, без долгих перелётов» доходит до оплаченной корзины с транспортом туда и обратно, отелем и двумя трансферами.
2. Сообщение «а если на два дня позже» пересобирает план без нового выбора направления.
3. Для гражданина Беларуси, который летит из Минска, подбор направлений и визовые пометки считаются по паспорту Беларуси.
4. Направление с визой, названное пользователем, принимается, а в плане есть проверка `visa` со статусом `fail`.
5. Цена заказа совпадает с итогом плана, повтор с тем же ключом идемпотентности не создаёт второй заказ.

## Non-Goals

- Всё из фазы 2 roadmap: аккаунты, память, работа после покупки, eval из 50 запросов.
- Маршруты по нескольким городам (ADR 0001).
- Транзитные визы, стоимость и сроки оформления виз (спека 0002).
- Живой скрейпинг коммерческих сайтов (`spec.md`, Q-004).
- Карта и визуальная шлифовка под референс — фаза 3; в фазе 1 только подключение токенов дизайн-системы (`spec.md`, 3.10).

## Точки стыковки (Cross-Feature Contracts)

Каждый работает независимо, пока соблюдает эти пять договорённостей. Нарушение любой ломает сборку целиком, поэтому каждая проверяется автоматически.

### CFC-1. Внешнее API: BE ↔ FE

- Источник правды — `api/openapi.yaml`. FE берёт типы только из `web/src/api/schema.ts` (`npm run gen:api`), BE проверяет ответы тестами `internal/apitest`.
- FE работает от моков (`VITE_MOCKS=1`) и не ждёт бэкенд. Новое поле в контракте сначала появляется в моках, затем в бэкенде.
- Проверка: CI (`web`, `go`), линт OpenAPI.

### CFC-2. Контракты поставщиков: агент ↔ провайдеры (обе стороны у BE)

- `proto/catalog`, `lodging`, `transport`, `transfer`, `booking`. Реализация выбирается `*_PROVIDER` (ADR 0002).
- Правило цен: `GetOffer` возвращает ту же цену, что поиск, при тех же входных данных. На этом стоит перепроверка цен в `booking`.
- Проверка: тесты провайдеров «поиск = `GetOffer`» и регенерация `gen/` в CI.

### CFC-3. Снапшот данных: DS → BE

DS готовит данные файлами, BE читает их при старте `inventory`. Никто не ходит во внешние API во время хода агента, кроме погоды Open-Meteo, как в фазе 0.

Раскладка:

```
data/
  requirements.txt          зависимости загрузчиков с версиями
  loaders/<источник>/       скрипты загрузки, по каталогу на источник
  overrides/                ручные правки поверх источников (visa.csv и т. п.)
  sources.yaml              реестр источников: и взятых, и рассмотренных
  build.py                  собирает snapshot/ из loaders/ и overrides/
  validate.py               проверяет snapshot/ по схемам ниже
  snapshot/
    manifest.json
    <набор>.jsonl
```

Формат наборов:

- JSON Lines, UTF-8, один объект на строку, поля в `snake_case`.
- Коды стран — ISO 3166-1 alpha-2 в верхнем регистре; аэропорты — IATA; координаты — `lat`, `lon` (WGS 84); даты — `YYYY-MM-DD`; деньги — целые рубли; часовые пояса — IANA.
- У каждого объекта стабильный `id`: от него BE считает seed синтетики, поэтому `id` не меняется между пересборками снапшота.
- Поле `sources` — список имён провайдеров из `sources.yaml`.

`manifest.json`:

```json
{
  "built_at": "2026-10-26T12:00:00Z",
  "datasets": [
    {"name": "visa", "file": "visa.jsonl", "records": 39402, "sha256": "…", "schema_version": 1}
  ]
}
```

`sources.yaml` — реестр для страницы «Откуда данные» (`spec.md`, раздел 6):

```yaml
- provider: passport-index-data
  title: Passport Index Data
  url: https://github.com/imorte/passport-index-data
  license: MIT
  kind: real            # real | synthetic | derived
  status: used          # used | considered
  used_for: [визовый режим]
  fetched_at: 2026-10-26T10:00:00Z
  reason: ""            # для considered — почему не взяли
```

Проверки:

- `data/validate.py` падает на нарушении схемы, дубле `id` или неизвестном имени в `sources`.
- `inventory` не стартует, если набора из манифеста нет на диске или `sha256` не совпадает (как с неизвестным `*_PROVIDER`).
- CI запускает `validate.py`, когда меняется `data/`.

Хранение: снапшот до 50 МБ лежит в git. Если больше — архив прикладывается к GitHub Release, а `scripts/fetch-data.sh` скачивает его по версии из `data/snapshot.version`; это потолок, а не стартовое решение.

### CFC-4. Фикстура моков: контракт ↔ FE

- `web/src/mocks/fixture.ts` повторяет контракт целиком и сверяется со схемой (`npm test`).
- PR, который меняет `api/openapi.yaml`, обновляет фикстуру в том же PR.

### CFC-5. Синтетика: DS → BE

- DS отдаёт параметры (`calibration`), BE пишет формулы.
- Цена детерминирована: seed — от `id` объекта и даты, как у отелей в фазе 0. Одинаковый вход — одинаковая цена в поиске и в `GetOffer`.
- Цены в рублях: зарубежные уровни цен переводятся по курсу ЦБ из `calibration`.

## Задачи

Поле «Приоритет»: **P0** — без задачи не выполняется цель фазы; **P1** — нужна по `spec.md`, но переносится в фазу 2, если фаза 1 не успевает.

### Бэкенд (BE)

#### P1-BE-01. Контракт виз и гражданства

- Приоритет: P0. Зависит от: мерж PR #1.
- Сделать: изменения из спеки 0002 в `api/openapi.yaml`, `proto/catalog/v1`, `internal/agent/plan` (новые поля, проверки, инвалидация), регенерация `gen/` и `web/src/api/schema.ts`; пустые реализации новых RPC (`UNIMPLEMENTED`).
- Готово, когда: CI зелёный; `redocly lint` без ошибок; тесты сверки со схемой проходят для `VisaRequirement`, `Country` и нового `TripPlan`.
- Не входит: загрузка визовых данных (`P1-BE-03`), интерфейс (`P1-FE-03`, `P1-FE-04`).

#### P1-BE-02. Загрузка снапшота в `inventory`

- Приоритет: P0. Зависит от: формат CFC-3.
- Сделать: пакет `internal/dataset` — чтение `manifest.json` и `*.jsonl` из `DATA_DIR` (по умолчанию `/data`), проверка `sha256`, индексы в памяти; тестовый снапшот в `internal/dataset/testdata/`; каталог `data/snapshot` в образе `inventory`.
- Готово, когда: `inventory` с неполным снапшотом завершается с кодом 1 и пишет имя недостающего набора; с тестовым снапшотом стартует и проходит `/readyz`.
- Не входит: сами данные (DS), хранение в PostgreSQL.

#### P1-BE-03. Провайдер `catalog` на снапшоте

- Приоритет: P0. Зависит от: `P1-BE-01`, `P1-BE-02`.
- Сделать: `ListCountries`, `GetVisaRequirement`, `SearchPlaces`, `SearchDestinations` (фильтры по тегам, времени в пути, бюджету, `visa_free_only`, `citizenship`; оценка полной стоимости и времени в пути; погода — климат по месяцу из `climate`, прогноз Open-Meteo в окне 14 дней). Имя провайдера — `open-data`, как в фазе 0.
- Готово, когда: «тёплое море в ноябре, гражданин RU» возвращает только направления с безвизовыми статусами и тегом `sea`; для `citizenship=BY` выдача считается по паспорту Беларуси; `no_admission` не возвращается никогда; `GetVisaRequirement` с неизвестным кодом отвечает `INVALID_ARGUMENT`.
- Не входит: объяснение выбора направления (агент, `P1-BE-08`).

#### P1-BE-04. Провайдер `lodging` на отелях OSM

- Приоритет: P0. Зависит от: `P1-BE-02`, CFC-5.
- Сделать: провайдер `osm` — отели из набора `hotels`, недостающие поля (звёзды, питание, отмена, животные) и цены генерируются детерминированно по `calibration`; туристический налог входит в цену проживания (`spec.md`, 3.5); `sources` — `osm` для места, `synthetic` для цены. Провайдер `synthetic` из фазы 0 остаётся вторым адаптером того же контракта (ADR 0002).
- Готово, когда: поиск и `GetOffer` дают одну цену; `LODGING_PROVIDER=synthetic` и `LODGING_PROVIDER=osm` оба работают; у каждого отеля `sources` с двумя провайдерами.
- Не входит: отзывы, фото.

#### P1-BE-05. Провайдер `transport` (авиа и ж/д)

- Приоритет: P0. Зависит от: `P1-BE-02`, CFC-5.
- Сделать: провайдер `synthetic` — авиа по `routes` и `airports` (время в пути по расстоянию, пересадка через хаб, если прямого маршрута нет), ж/д по `rail_routes` (реальное расписание, синтетическая цена); время в часовом поясе места (RFC 3339); `GetOffer` по идентификатору варианта.
- Готово, когда: Москва — Сочи на дату возвращает и авиа, и ж/д; Минск — Пекин возвращает авиа; цена за всех пассажиров учитывает возраст детей; поиск и `GetOffer` дают одну цену.
- Не входит: реальные цены авиакомпаний, бронирование мест.

#### P1-BE-06. Провайдер `transfer`

- Приоритет: P0. Зависит от: `P1-BE-02`, CFC-5.
- Сделать: провайдер `synthetic` — такси, шаттл и общественный транспорт между аэропортом или вокзалом и отелем; время по расстоянию с коэффициентом города, цена по тарифу из `calibration`, отдельный тариф с животным.
- Готово, когда: для любой пары «аэропорт — отель» из снапшота есть минимум два вида трансфера; с `pets=true` у такси цена выше; поиск и `GetOffer` дают одну цену.
- Не входит: маршрутизация по дорогам (OSRM) — потолок, подключается, когда время в пути заметно расходится с реальностью.

#### P1-BE-07. Сборка полной поездки и валидатор стыковок

- Приоритет: P0. Зависит от: `P1-BE-04`, `P1-BE-05`, `P1-BE-06`.
- Сделать: агент ищет и перепроверяет все пять компонентов плана; валидатор (детерминированный код) заполняет `checks`: `arrival_before_checkin`, `transfer_fits`, `checkout_before_departure`, `dates_consistent`, `visa`, `stay_within_visa_free_days`; интервалы — из `config/rules.yaml`; гейты этапов `assemble` и `checkout` (ADR 0001).
- Готово, когда: «на два дня позже» перепроверяет все компоненты без нового выбора направления; прилёт после времени заселения с учётом трансфера даёт `warn`; рейс обратно раньше выезда из отеля с учётом буфера даёт `fail`.
- Не входит: LLM-объяснения (`P1-BE-09`).

#### P1-BE-08. Этап вдохновения в агенте

- Приоритет: P0. Зависит от: `P1-BE-03`.
- Сделать: если направление не названо, агент вызывает `SearchDestinations` и заполняет `destination_options` (до 5 вариантов) с объяснением; выбор направления — сообщением или патчем `destination`.
- Готово, когда: запрос без направления даёт этап `inspire` и не меньше трёх вариантов с ценой, погодой, временем в пути и визовым статусом.
- Не входит: память о прошлых поездках (фаза 2).

#### P1-BE-09. Цикл вызова инструментов на LLM

- Приоритет: P1. Зависит от: `P1-BE-07`, `P1-BE-08`.
- Сделать: на каждом этапе модель видит только инструменты этапа, не больше N шагов за ход (ADR 0001); объяснения вариантов `why`, `tradeoffs`, `risks` из данных плана; без ключа LLM — правила и шаблоны, сценарий проходится.
- Готово, когда: с ключом у каждого рекомендованного варианта заполнено `explanation`; без ключа цель фазы выполняется целиком.
- Не входит: подбор моделей (Q-001).

#### P1-BE-10. Роутер: новые поля

- Приоритет: P0. Зависит от: `P1-BE-01`.
- Сделать: `origin`, `citizenship`, строгость бюджета, теги настроения, виды транспорта, максимум часов в пути, «можно с визой» → `visa_free_only=false`; правила (без LLM) и промпт роутера.

## Риски

- **Один бэкендер на 13 задач.** Задачи P1 (`P1-BE-09`, `P1-BE-12`, `P1-BE-13`) переносятся в фазу 2, если к середине дня 3 не готовы задачи P0. Цель фазы при этом выполняется на правилах без LLM.
- **Объём данных вырос из-за зарубежных направлений.** Каталог направлений курируемый, а не «вся планета»: DS добавляет направления, пока успевает загрузить для них отели и маршруты.
- **Визовые данные — справочные.** Дату обновления показываем на странице «Откуда данные».

## Decision Log

- **Роли вместо треков.** Треки A и B roadmap объединены в роль BE, потому что бэкендер один; сбор данных стал отдельной ролью DS с собственным владением `data/`.
- **Данные — файлами, а не в PostgreSQL.** Снапшот читается в память `inventory`: данные только для чтения и меняются вместе с релизом; DS не нужен доступ к базе. Потолок: переносим в PostgreSQL, когда снапшот перестанет помещаться в память одного процесса.
- **DS пишет на Python, BE — на Go.** Загрузчики данных одноразовые и меняются часто, на Python их быстрее писать; стык — только файлы CFC-3, поэтому языки не смешиваются.
- **Провайдер `synthetic` у `lodging` остаётся.** ADR 0002 требует два адаптера одного контракта на демо; `osm` и `synthetic` дают это без лишней работы.
- **Нумерация задач `P1-<роль>-<номер>`.** Фаза, роль и порядковый номер; номера не переиспользуются.
