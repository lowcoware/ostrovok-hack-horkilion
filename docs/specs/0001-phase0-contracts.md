# Спека 0001. Фаза 0: контракты

- Статус: inbox
- Дата: 2026-10-25
- Основание: [roadmap](../roadmap.md), фаза 0; [ADR 0002](../adr/0002-reusable-agent-platform.md); [ADR 0001](../adr/0001-architecture.md)
- Ревью: Ask. Контракты задевают все сервисы и фронт, поэтому ревью синхронное, всей командой, до мержа.

## Context

Три трека начинают работу параллельно. Пока контракты не зафиксированы, фронт ждёт бэкенд, а два бэкендера правят одни и те же структуры. Сейчас контракты описывают только сценарий «отель в городе»: `TripPlan` в `internal/agent/plan.go` знает только отели и одно направление, внешнее API описано лишь кодом gateway и вручную продублировано в `web/src/api.ts`, а proto содержит один сервис `inventory` без транспорта, трансферов и поля происхождения данных.

Эта спека фиксирует внешнее API, `TripPlan` v2, контракты поставщиков и конфиг. Логику агента, загрузку данных и интерфейс она не реализует.

## Non-Goals

- Реализация поиска транспорта, трансферов и направлений: это фаза 1, здесь только контракты и заглушки.
- Контракты работы после покупки (смена дат, ранний заезд, трансфер к купленному отелю): отдельная спека фазы 2, она расширит контракт через PR.
- Реализация регистрации и входа: в фазе 0 только эндпоинты в OpenAPI и модель владельца сессии.
- Загрузка реальных данных и второй адаптер поставщика.
- Дизайн интерфейса.

## Assumptions

- Go-модуль `horkilion`, генерация proto через `scripts/gen-proto.sh`, сгенерированный код лежит в `gen/` (как сейчас).
- Фронт — React и TypeScript в `web/`, сборка через Vite.
- Внешних клиентов API пока нет, поэтому старый `/api/...` удаляется без периода совместимости.

## Design Principles

- Переиспользуемость первична (ADR 0002): каждый внешний источник данных стоит за контрактом поставщика, агент — самостоятельное API.
- Одна схема `TripPlan` для агента, фронта и eval (ADR 0001, раздел «Состояние»).
- Контракт — источник правды, код генерируется из него. Ручных копий типов нет.
- Деньги — целые рубли (`int64`), время — RFC 3339 с часовым поясом места, даты — `YYYY-MM-DD`.

## Data Model / Contract

### Раскладка файлов

| Путь | Что |
|---|---|
| `api/openapi.yaml` | Внешнее API, OpenAPI 3.1 |
| `proto/common/v1/common.proto` | `Source`, `GeoPoint`, `Place` |
| `proto/catalog/v1/catalog.proto` | Направления и погода |
| `proto/lodging/v1/lodging.proto` | Отели и предложения |
| `proto/transport/v1/transport.proto` | Авиа и ж/д |
| `proto/transfer/v1/transfer.proto` | Трансферы |
| `proto/booking/v1/booking.proto` | Заказ из нескольких позиций, имитация оплаты |
| `config/rules.yaml` | Бизнес-правила |
| `web/src/api/schema.ts` | TS-типы, сгенерированные из OpenAPI |
| `web/src/mocks/` | Моки API и фикстура полной поездки |

`proto/inventory/v1` удаляется, его RPC расходятся по `catalog` и `lodging`.

### Происхождение данных

Каждое сообщение поставщика, которое попадает к пользователю (направление, отель, предложение, рейс, трансфер, погода), содержит `repeated common.v1.Source sources`:

```proto
message Source {
  string provider = 1;        // machine name: "osm", "ourairports", "open-meteo", "synthetic"
  Kind kind = 2;              // REAL, SYNTHETIC, DERIVED (computed from real data)
  string field_scope = 3;     // which fields this source covers: "location", "price", "*"
  string url = 4;             // dataset or API page, empty for synthetic
  string license = 5;         // "ODbL-1.0", "CC-BY-4.0", ...
  google.protobuf.Timestamp fetched_at = 6;
}
```

Источников несколько, потому что у одного отеля координаты и название могут быть из OSM, а цена синтетическая. В JSON внешнего API то же самое — массив `sources` с теми же полями.

### Контракты поставщиков

Каждый сервис поставщика может иметь несколько реализаций. Реализация выбирается переменной окружения процесса: `CATALOG_PROVIDER`, `LODGING_PROVIDER`, `TRANSPORT_PROVIDER`, `TRANSFER_PROVIDER`. Неизвестное значение — ошибка запуска.

| Сервис | RPC | Ключевые поля |
|---|---|---|
| `catalog.v1.CatalogService` | `SearchDestinations` | Вход: откуда, даты или месяц, путешественники, бюджет, теги (`sea`, `warm`, `kids`, `nature`...), максимум часов в пути, только Россия и безвиз. Выход: направление (id, название, страна, `Place`, теги, оценка полной стоимости, время в пути, погода, `sources`) |
| | `GetWeather` | Место и даты → температура, осадки, прогноз или климатическая норма (`kind`), `sources` |
| `lodging.v1.LodgingService` | `SearchHotels` | Место, проживание (заезд, ночи, взрослые, возраст детей, животные), фильтры. Выход: отель (как `Hotel` сейчас, плюс `Place`, время заезда и выезда, условия отмены текстом, `sources`) |
| | `GetOffer` | id предложения и проживание → актуальная цена; цена совпадает с поиском при тех же входных данных |
| `transport.v1.TransportService` | `SearchJourneys` | Откуда, куда, дата, пассажиры, виды (`AIR`, `RAIL`). Выход: вариант пути из сегментов (перевозчик, номер, откуда, куда, отправление, прибытие), длительность, пересадки, багаж, возвратность, цена, `sources` |
| | `GetOffer` | id варианта → актуальная цена |
| `transfer.v1.TransferService` | `SearchTransfers` | Откуда и куда (`Place`), время, пассажиры. Выход: вид (такси, шаттл, общественный транспорт), длительность, цена, `sources` |
| `booking.v1.BookingService` | `CreateOrder` | Ключ идемпотентности, владелец, позиции (`kind`, id предложения, цена, которую видел пользователь). Booking заново запрашивает цену каждой позиции у её поставщика; если цена изменилась, заказ не создаётся и возвращается `FAILED_PRECONDITION` с новыми ценами |
| | `GetOrder`, `ListOrders` | По владельцу |

Владелец передаётся в metadata gRPC (`x-owner-id`), а не в теле запроса.

### TripPlan v2

Одна JSON-схема в `api/openapi.yaml`, Go-структуры в `internal/agent` ей соответствуют. Верхний уровень:

| Поле | Смысл |
|---|---|
| `session_id`, `version`, `stage` | Как сейчас; этапы те же, что в `plan.go` |
| `constraints` | Откуда, направление (или пусто), даты (`depart`, `return` либо `nights`), гибкость дат в днях, взрослые, возраст детей, животные, бюджет (сумма и строгий он или ориентир), предпочтения (питание, бесплатная отмена, виды транспорта, максимум часов в пути, теги настроения) |
| `assumptions` | Как сейчас: поле, значение, причина |
| `destination_options` | Варианты направлений этапа вдохновения: направление из `catalog`, объяснение |
| `components` | `outbound`, `stay`, `return`, `transfer_arrival`, `transfer_departure`; у каждого `options` и `selected_id` |
| `checks` | Проверки стыковок: вид (`arrival_before_checkin`, `transfer_fits`, `checkout_before_departure`, `dates_consistent`), статус (`ok`, `warn`, `fail`), текст, ссылки на компоненты |
| `conflicts` | Как сейчас, плюс ссылки на компоненты |
| `total_rub`, `over_budget` | Сумма выбранного |

Каждый вариант внутри компонента:

```json
{
  "id": "…",
  "kind": "stay | journey | transfer",
  "offer": { "…поля предложения поставщика…" },
  "price_rub": 39500,
  "explanation": {
    "why": "почему подходит этому пользователю",
    "tradeoffs": ["чем пришлось пожертвовать"],
    "risks": ["какие риски"]
  },
  "flags": ["over_budget", "selected_unavailable"],
  "sources": [ { "provider": "osm", "kind": "real", "field_scope": "location" } ]
}
```

### Патч плана

Ручная правка карточек на фронте и текстовые сообщения меняют план через один механизм. Патч — объект с теми же полями, что `constraints`, все поля необязательные; плюс выбор варианта: `{ "select": { "component": "stay", "option_id": "…" } }`. Инвалидация по таблице ADR 0001 действует для обоих источников.

### Внешнее API

Префикс `/api/v1`. Все ответы JSON, ошибки в формате `{ "error": { "code": "…", "message": "…" } }`.

| Метод и путь | Что |
|---|---|
| `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /me` | Аккаунт. Реализация в фазе 2, в фазе 0 только схема |
| `POST /sessions` | Новая поездка |
| `GET /sessions` | Поездки владельца |
| `GET /sessions/{id}` | План и история сообщений |
| `POST /sessions/{id}/messages` | Сообщение пользователя (до 2000 символов), ответ `202` с `message_id` |
| `POST /sessions/{id}/plan` | Патч плана с фронта, ответ `202`, результат приходит событием |
| `GET /sessions/{id}/events` | SSE |
| `POST /sessions/{id}/checkout` | Заказ из выбранных вариантов, заголовок `Idempotency-Key` (UUID) обязателен |
| `GET /orders`, `GET /orders/{id}` | Заказы владельца |
| `GET /sources` | Список провайдеров данных с описанием, лицензией и датой загрузки — для страницы «Откуда данные» |

Владелец — анонимный идентификатор из cookie, которую gateway выставляет при первом запросе, или аккаунт после входа (ADR 0002). Сессия или заказ другого владельца отвечает `404`, чтобы не раскрывать, что такой id существует.

### События SSE

Конверт: `{ "type", "session_id", "turn_id", "seq", "data" }`. `seq` растёт внутри сессии; после переподключения клиент делает `GET /sessions/{id}` и продолжает с актуального плана.

| `type` | `data` |
|---|---|
| `status` | Этап и короткий текст («ищу перелёты») |
| `token` | Фрагмент ответа агента |
| `plan` | Полный `TripPlan` с новой версией |
| `clarify` | Вопрос и варианты быстрых ответов |
| `done` | Итоговое сообщение агента |
| `error` | Код и текст |

### Конфиг

- LLM: `LLM_BASE_URL` (по умолчанию OpenRouter), `LLM_API_KEY`, `LLM_MODEL`, `LLM_ROUTER_MODEL`, `LLM_EXTRA_BODY` (JSON, по умолчанию `{"provider":{"data_collection":"deny"}}`). `OPENROUTER_API_KEY` читается как запасное имя ключа до конца фазы 1.
- Поставщики: переменные `*_PROVIDER` выше.
- Бизнес-правила в `config/rules.yaml`: минимальное время между прилётом и заселением с учётом трансфера, буфер перед вылетом, максимум уточняющих вопросов за ход, наценка в процентах. Agent читает файл при старте, неверный файл — ошибка запуска.

## Runtime Behavior

Фаза 0 поведения не добавляет. После мержа:

1. `scripts/gen-proto.sh` генерирует Go-код для всех proto, генерация TS из OpenAPI идёт командой `npm run gen:api` в `web/`.
2. Новые RPC поставщиков возвращают `UNIMPLEMENTED`, кроме отелей и погоды: они переезжают из `inventory` с текущей синтетикой.
3. Gateway отвечает по `/api/v1`, агент собирает `TripPlan` v2: компонент `stay` заполнен, остальные пустые.
4. Фронт в режиме моков (`VITE_MOCKS=1`) работает без бэкенда: моки отдают фикстуру полной поездки и проигрывают последовательность событий SSE одного хода.

Отказы:

- Если сгенерированный код не совпадает с контрактом, CI падает.
- Если поставщик в конфиге неизвестен, процесс не стартует и пишет в лог допустимые значения.

## Testing Strategy

| Что | Как |
|---|---|
| OpenAPI валиден | `redocly lint api/openapi.yaml` в CI |
| Сгенерированный код актуален | CI заново генерирует proto и TS и проверяет `git diff --exit-code` |
| Gateway соответствует OpenAPI | Тест gateway проверяет по схеме (`kin-openapi`) ответы `POST /sessions`, `GET /sessions/{id}`, `POST /sessions/{id}/messages`, `POST /sessions/{id}/checkout` и ошибок `400`, `404` |
| Фикстура моков соответствует схеме | Тест фронта проверяет фикстуру по сгенерированным типам и схеме |
| Владение сессией | Тест gateway: чужая сессия → `404` |
| Сквозной сценарий не сломан | Текущий ручной сценарий (поиск отеля → заказ, цена заказа равна цене плана) на compose-стеке |

## Decision Log

- **`/api/v1` вместо `/api`.** Версия в пути дешевле всего обходится внешним клиентам, а внешний клиент — цель ADR 0002.
- **Типы Go для внешнего API пишутся руками, соответствие проверяется тестом по схеме.** Рассматривали генерацию серверного кода через `oapi-codegen`, но handlers gin уже есть, а проверка по схеме ловит то же расхождение без второго генератора.
- **TS-типы генерирует `openapi-typescript`.** Только типы, без рантайм-клиента; клиент — тонкий `fetch`, как сейчас.
- **Моки на MSW, а не на Prism.** Prism не умеет SSE, а без SSE фронт не проверит главный экран.
- **Поставщики разделены по видам (`catalog`, `lodging`, `transport`, `transfer`), а не один `inventory`.** Островок подключает свой API отелей, оставляя наш транспорт, и наоборот.
- **Несколько `sources` на сущность.** У одной сущности поля приходят из разных источников; один флаг `synthetic`, как сейчас, это скрывает.
- **Booking перепроверяет цены у поставщиков и отказывает при расхождении.** Пользователь не должен заплатить не ту цену, которую видел; это уже сломалось один раз (надбавка за животных).
- **Возраст детей вместо числа детей.** От возраста зависят цена билета и размещение. Если возраст не назван, агент берёт допущение и показывает его.

## Acceptance Criteria

1. Репозиторий содержит `api/openapi.yaml`, который проходит `redocly lint` без ошибок.
2. Если `api/openapi.yaml` изменён, а `web/src/api/schema.ts` не перегенерирован, CI падает.
3. Если файл в `proto/` изменён, а `gen/` не перегенерирован, CI падает.
4. Фронт собирается на сгенерированных типах, в `web/src` не остаётся вручную написанных типов ответов API.
5. Когда фронт запущен с `VITE_MOCKS=1` без бэкенда, он показывает план с транспортом туда и обратно, отелем, двумя трансферами и проверками стыковок.
6. Когда фронт запущен с `VITE_MOCKS=1`, отправленное сообщение проигрывает события `status`, `token`, `plan` и `done`.
7. Каждое сообщение поставщика, которое показывается пользователю, содержит поле `sources`.
8. Если запрос обращается к сессии другого владельца, gateway отвечает `404`.
9. Если `*_PROVIDER` содержит неизвестное значение, процесс завершается с ошибкой при старте.
10. Сквозной сценарий «поиск отеля → заказ» проходит на compose-стеке после перехода на `/api/v1` и `TripPlan` v2, цена заказа совпадает с ценой в плане.

## Задачи

Порядок важен только в первом пункте, дальше параллельно.

1. **Все вместе, первые 1–2 часа:** схема `TripPlan` v2 и событий SSE в `api/openapi.yaml`. Это общий язык трёх треков, его ревьюят все до начала остального.
2. **Трек A:** Go-структуры `TripPlan` v2 и патча, перевод агента на них, тест соответствия схеме, `config/rules.yaml` и его загрузка, переменные `LLM_*`.
3. **Трек B:** proto v2 с `Source`, перенос отелей и погоды из `inventory`, заглушки остальных RPC, выбор поставщика по `*_PROVIDER`, booking с позициями и перепроверкой цен, владелец в metadata, CI-проверка `gen/`.
4. **Трек F:** остальные эндпоинты в `api/openapi.yaml`, генерация типов, MSW и фикстура полной поездки, перевод `api.ts` на `/api/v1`, CI-проверки OpenAPI и TS.
5. **Трек A или B, после 2–4:** gateway на `/api/v1`, cookie владельца и проверка владения, тест по схеме, прогон сквозного сценария.

Нет. Вопрос о моделях и ключах (roadmap, Q-001) на контракт не влияет: провайдер настраивается переменными `LLM_*`.
