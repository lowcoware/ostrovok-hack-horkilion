# ADR 0001. Архитектура агента: Go, React и граф этапов с гейтами

- Статус: proposed
- Дата: 2026-10-23
- Связанные документы: [кейс](../case.md), [выбор моделей](../models.md)

## Контекст

Нужен прототип агента, который проводит пользователя от одного сообщения до имитированной покупки. Жюри будет задавать запросы, которых мы заранее не видели. Кейс прямо требует, чтобы агент пересобирал план при изменении условий, а не искал всё заново, и чтобы пользователь понимал логику выбора.

Ограничения:

- модели только с открытыми весами через OpenRouter, OpenAI-совместимый API (см. `models.md`);
- open-weights модели ошибаются в tool calling чаще закрытых, поэтому чем меньше инструментов видит модель за один шаг, тем надёжнее;
- команда выбрала Go для бэкенда и React с библиотекой компонентов Magic UI для фронтенда.

## Решение

### Стек

| Слой | Выбор |
|---|---|
| Бэкенд | Go, несколько сервисов в одном Go-модуле (monorepo), HTTP на Gin, стриминг событий фронту через SSE |
| LLM-клиент | официальный `github.com/openai/openai-go` v3, `base_url` указывает на OpenRouter |
| Оркестрация | свой граф этапов на Go (описан ниже), без фреймворка |
| База данных | PostgreSQL 18, драйвер `jackc/pgx` v5, миграции `pressly/goose` v3 |
| Брокер сообщений | NATS JetStream (сервер 2.15, клиент `nats-io/nats.go`) |
| Кэш и эфемерное состояние | NATS KV (часть JetStream), отдельный Redis не нужен |
| Связь между сервисами | синхронные вызовы по gRPC (`google.golang.org/grpc`), контракты в `.proto` в общем каталоге `proto/` монорепозитория; асинхронные потоки (очередь ходов агента, события бронирования) остаются на NATS JetStream |
| Наблюдаемость | OpenTelemetry: метрики → Prometheus + Grafana; трейсы, включая каждый вызов LLM и инструмента, → self-hosted Langfuse через OTLP |
| Продуктовая аналитика | ClickHouse, который уже входит в self-hosted Langfuse v3: отдельная база `analytics` с событиями воронки, дашборды в Grafana через плагин ClickHouse |
| Фронтенд | React + TypeScript + Vite, Tailwind, компоненты и анимации Magic UI (поверх shadcn/ui, компоненты добавляются в проект через shadcn CLI) |
| Данные | справочные данные реальные, из открытых источников (погода, аэропорты, отели и POI, расписания, контент о направлениях); цены, наличие и условия синтетические поверх них. Полный список в разделе «Источники данных» |
| Оплата | имитация через отдельный сервис с теми же гарантиями, что у настоящей (идемпотентность, outbox) |
| Мобильная версия (доп. задача) | Адаптивная вёрстка того же веб-клиента. Мессенджеры (Telegram, MAX) не делаем |
| Запуск | Docker Compose: все сервисы, PostgreSQL, NATS, наблюдаемость одной командой |

### Сервисы

| Сервис | Ответственность |
|---|---|
| `gateway` | HTTP API и SSE для фронта и других клиентов агента, аутентификация, rate limiting. Принимает сообщение, кладёт его в очередь, ретранслирует события агента в SSE |
| `agent` | воркеры, которые выполняют ход агента: роутер, инвалидация, граф этапов, вызовы LLM и инструментов, валидатор. Масштабируются горизонтально |
| `inventory` | поиск и цены по отелям, перелётам, ЖД, трансферам (поверх синтетических данных), погода с кэшем |
| `booking` | корзина, оформление, имитация оплаты, изменения брони после покупки |
| `notifier` | напоминания и уведомления на сайте по событиям бронирования |

`# impulse: один Go-модуль и общая PostgreSQL со схемой на каждый сервис; делим на отдельные базы, когда у сервисов появятся разные требования к нагрузке или релизному циклу.`

### Потоки через брокер

- **Ход агента.** `gateway` публикует сообщение пользователя в поток `AGENT_TURNS`. Воркер `agent` забирает его, выполняет ход и публикует события (токены, вызовы инструментов, обновление `TripPlan`) в `session.<id>.events`. `gateway` ретранслирует их в SSE. Если воркер падает посреди хода, сообщение не подтверждено и уходит другому воркеру. Ходы одной сессии обрабатываются строго по порядку: на сессию держится лок в NATS KV.
- **Бронирование.** `booking` пишет заказ и событие в одной транзакции PostgreSQL (transactional outbox), отдельный релеер публикует событие в поток `BOOKINGS`. `notifier` и `agent` (для этапа `post_purchase`) подписаны на этот поток.
- **Синхронные запросы** между сервисами идут по gRPC: `agent` → `inventory` (поиск, цены, погода) и `agent` → `booking` (корзина, оформление). У каждого вызова есть дедлайн, повторяются только идемпотентные методы.
- **Аналитика.** `agent` и `booking` пачками пишут события воронки (`session_started`, `stage_entered`, `option_selected`, `plan_rebuilt`, `checkout_completed`) в базу `analytics` в ClickHouse. Воронку и отвал по этапам считает `windowFunnel`, дашборды строятся в Grafana.

`# impulse: аналитика живёт в ClickHouse от Langfuse, в отдельной базе; выносим в свой инстанс, когда нагрузка аналитики начнёт мешать Langfuse или понадобятся разные сроки хранения.`

### Надёжность

- Источник правды — PostgreSQL: `TripPlan` хранится как версионированный JSONB, бронирования и платежи — в нормализованных таблицах. Каждый ход агента пишет новую версию плана, поэтому изменения можно откатить и показать пользователю диф «что поменялось».
- Оформление заказа идемпотентно: ключ идемпотентности приходит с фронта, повторный клик или ретрай не создаёт второй заказ.
- Все внешние вызовы (OpenRouter, Open-Meteo) идут с таймаутами, ретраями с backoff и circuit breaker. Если основная модель недоступна, используется запасная из `models.md`.
- Консьюмеры идемпотентны (дедупликация по ID сообщения), сообщения, которые не удалось обработать после N попыток, уходят в dead-letter поток.
- Graceful shutdown во всех сервисах: дообработка текущего хода, без подтверждения недоделанных сообщений.
- Health и readiness пробы, структурированные логи с `trace_id`, сквозной трейс от сообщения пользователя до каждого вызова LLM.

### Источники данных

Реальных бесплатных API с живыми ценами и наличием мест по отелям, билетам и трансферам нет. Поэтому справочные данные берём реальные, а цены, наличие и условия генерируем поверх них. На демо прямо говорим, что именно синтетическое.

Источники проверены поиском 2026-10-24. Пометка «проверить» означает, что лимит или лицензия подтверждены только сторонними источниками, а не документацией владельца.

#### Что генерируем

- Цены на ночь с сезонностью: сезон по климату, праздники из Nager.Date, калибровка по Hotel Booking Demand.
- Наличие номеров, тип питания, условия отмены, правила для животных и детей.
- Цены на авиабилеты вокруг уровня из Aviasales Data API, время полёта по расстоянию между аэропортами.
- Цены на ЖД поверх реального расписания из Яндекс Расписаний.
- Трансферы: время из OSRM, цена по формуле от расстояния и типа машины, с животным отдельный тариф.

Синтетика привязана к реальным точкам OSM, поэтому агент работает в любом городе, где есть отели. Для популярных направлений данные готовит seed-команда, для остальных городов они генерируются при первом запросе. Seed берётся от идентификатора отеля и даты, чтобы цены не менялись между ходами.

На вопрос жюри про применимость в бизнесе: Open-Meteo, Яндекс Расписания и openrouteservice бесплатны только для некоммерческого или открытого использования. В проде это платная подписка или свой инстанс, как и с OpenRouter.

### Состояние: TripPlan, а не история чата

Единственный источник правды о поездке — структурированный объект `TripPlan`. В нём лежат:

- `constraints`: бюджет, даты или окно дат, состав гостей (включая детей и животных), откуда едем, ограничения (длительность перелёта, питание, отмена), настроение поездки;
- `stage`: текущий этап;
- `destination`, `options` (найденные варианты), `selected` (выбранные отель, перелёт, трансфер);
- `cart`, `booking` (после покупки);
- `conflicts`: найденные проблемы состыковки и нарушения ограничений;
- `assumptions`: что агент предположил сам, чтобы показать это пользователю и дать поправить.

История чата нужна для тона разговора, но решения принимаются по `TripPlan`. Фронтенд рисует тот же объект: план, корзину, прогресс по этапам.

### Граф этапов: гейты вместо жёстких рёбер

Этапы из кейса: `clarify` → `inspire` → `search` → `compare` → `assemble` → `checkout` → `post_purchase`.

Граф не задаёт, из какого узла в какой можно перейти. Вместо этого у каждого этапа есть **гейт**: предикат над `TripPlan`, который говорит, достаточно ли данных, чтобы войти в этап. Например, для `search` нужны направление, даты и состав гостей, для `checkout` — непустая корзина без блокирующих конфликтов.

Из этого правило перехода: агент идёт на этап, который просит пользователь, но если гейт не пройден, он попадает на самый ранний этап с непройденным гейтом и спрашивает только недостающее. Так соблюдается требование «никакой анкеты из 15 вопросов»: вопрос задаётся, только когда без ответа нельзя пройти конкретный гейт.

### Обработка одного сообщения

1. **Роутер.** Лёгкая модель возвращает структурированный JSON: список намерений (в одном сообщении их может быть несколько), патч к `constraints` и желаемый этап. Намерения: `provide_info`, `change_constraint`, `select_option`, `ask_question`, `go_to_stage`, `post_purchase_request`, `off_topic`, `unknown`.
2. **Применение патча и инвалидация** (детерминированный Go-код, без LLM). В коде задана таблица зависимостей: что устаревает при изменении каждого поля. Сдвиг дат проверяет заново перелёт, отель и трансфер. Собака в составе гостей перефильтровывает отели по правилам для животных и меняет тип трансфера. Уменьшение бюджета пересчитывает итог корзины и помечает варианты, которые в него не влезают. Всё, что не затронуто, остаётся как было. Это и есть пересборка без поиска с нуля.
3. **Выбор этапа** по гейтам, как описано выше.
4. **Узел этапа.** Модель получает промпт этапа и только инструменты этого этапа и делает цикл tool calling, не больше N шагов за ход.
5. **Валидатор** (детерминированный Go-код): состыковки по времени (прилёт, дорога до отеля, время заселения), бюджет, соответствие ограничениям. Найденное пишется в `conflicts`, и агент обязан сказать о нём пользователю.
6. **Ответ.** Текст и обновлённый `TripPlan` уходят на фронт событиями SSE.

### Нестандартные запросы

| Пример запроса | Как обрабатывается |
|---|---|
| «а если на два дня позже?» | `change_constraint` → сдвиг дат → инвалидация перелёта, отеля и трансфера → повторная проверка тех же вариантов на новые даты, новый поиск только для тех, что отпали |
| «с нами едет собака» | патч состава гостей → перефильтрация отелей и трансфера, в `conflicts` попадают выбранные варианты, которые больше не подходят |
| «бюджет меньше» | патч бюджета → пересчёт корзины, агент предлагает, чем пожертвовать, и объясняет компромисс |
| «уже купил отель в другом месте, нужен трансфер» | `post_purchase_request` с внешним бронированием: гейт `post_purchase` принимает данные брони, введённые пользователем |
| «хочу к морю, но и в горы» | роутер возвращает два ограничения на настроение, `inspire` ищет направления, где есть и то и другое |
| «а сколько стоит виза в Турцию?» | `off_topic` в рамках поездки: короткий ответ без инструментов, этап не меняется |
| несколько намерений сразу («давай второй отель, и ещё найди трансфер») | роутер возвращает список, намерения применяются по порядку в одном ходе |
| роутер не смог классифицировать | `unknown` → свободный узел: модель со всеми инструментами только для чтения, без права менять корзину и оформлять заказ |

`# impulse: одно направление на поездку; маршруты по нескольким городам добавляем, если на прогоне тестовых запросов они окажутся частыми.`

### Почему свой граф, а не фреймворк

Узлов семь, переход считается одной функцией по гейтам. На Go это switch по этапу и реестр инструментов, сотни строк, которые команда понимает целиком и может объяснить на защите. Eino (`cloudwego/eino`) живой и умеет графы, но он ещё в версии 0.x, его надо изучать, и его модель «узлы и рёбра» хуже подходит к логике гейтов.

`# impulse: свой граф; переходим на Eino, если появятся параллельные ветки или граф вырастет больше десятка узлов.`

## Рассмотренные альтернативы

- **Python + FastAPI, свой цикл агента.** Лучшая экосистема для LLM и прогонов, но команда выбрала Go. Тестовый прогон на Go тоже пишется без проблем: это набор запросов и проверки над `TripPlan`.
- **Fullstack TypeScript + Vercel AI SDK.** Самый быстрый путь к UI в чате, но логика агента оказывается внутри абстракций SDK, а Go на бэкенде уже выбран.
- **Классический граф с явными рёбрами (в стиле LangGraph).** Наглядный, но незнакомые запросы жюри требуют прыжков между этапами, а каждый новый прыжок означает новое ребро. Гейты дают ту же наглядность (прогресс по этапам на фронте) без этой проблемы.
- **Kafka вместо NATS.** Стандарт для событийных шин, но плохо подходит для очередей задач: нет подтверждения отдельных сообщений и отложенной доставки, а в эксплуатации Kafka тяжелее. Наша нагрузка — это очереди задач (ходы агента) и умеренный поток событий бронирования, а не аналитический стриминг.
- **RabbitMQ вместо NATS.** Зрелый брокер для очередей задач, но для KV, request-reply и стриминга токенов в реальном времени понадобились бы ещё Redis и отдельный транспорт. NATS JetStream закрывает всё это одним бинарником с нативным Go-клиентом.
- **NATS request-reply вместо gRPC для синхронных вызовов.** Одним компонентом меньше, но контракты между сервисами остаются нетипизированными. gRPC даёт строгие контракты в protobuf, кодогенерацию для Go и дедлайны из коробки.
- **Без брокера, всё через PostgreSQL (`LISTEN/NOTIFY`, очередь на `SKIP LOCKED`).** Меньше компонентов, но стриминг токенов и горизонтальное масштабирование воркеров агента решаются хуже.
- **Один свободный агент без этапов.** Максимально гибкий, но open-weights модель со всеми инструментами сразу ошибается чаще, а этапы на фронте пришлось бы угадывать. Свободный агент остался как запасной узел для `unknown`.

## Последствия

- Плюсы: пересборка плана закрывается детерминированным кодом, без надежды на LLM; модель на каждом шаге видит мало инструментов; логика объяснима; фронт и агент работают с одним объектом.
- Плюсы инфраструктуры: ход агента переживает падение воркера, бронирование не теряется и не дублируется, воркеры агента масштабируются независимо от остального.
- Минусы: таблицу зависимостей и гейты пишем и поддерживаем вручную; качество роутера становится критичным, поэтому он первым попадает в тестовый прогон.
- Минусы инфраструктуры: пять сервисов, PostgreSQL, NATS и стек наблюдаемости съедают время команды на старте. Порядок работ такой: сначала сквозной сценарий через `gateway` и `agent` на PostgreSQL и NATS, затем `booking` с outbox, затем `notifier` и наблюдаемость.
- Что поменяет решение: если на прогоне роутер ошибается больше чем в 10–15% запросов, отказываемся от отдельного роутера и отдаём классификацию основной модели в том же вызове, что и ответ.
