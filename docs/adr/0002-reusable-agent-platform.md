# ADR 0002. Переиспользуемость: адаптеры поставщиков, агент как API, аккаунты, запуск для жюри

- Статус: proposed
- Дата: 2026-10-25
- Дополняет: [ADR 0001](0001-architecture.md)
- Связанные документы: [roadmap](../roadmap.md), [кейс](../case.md), [модели](../models.md)

## Контекст

Критерии оценки в порядке важности: переиспользуемость решения реальным бизнесом, затем архитектура, затем внешний вид. Отдельно команда отвечает за то, чтобы жюри было удобно проверить и запустить решение. Вопрос о внешних моделях и ключах организаторы решат позже.

ADR 0001 описывает устройство агента: `TripPlan` как состояние, граф этапов с гейтами, на каждом этапе цикл вызова инструментов с ограниченным набором, детерминированная инвалидация. Это устройство остаётся. Но ADR 0001 не отвечает на вопросы, которые задаст бизнес: как подключить свой инвентарь, как встроить агента в свой продукт, на каких моделях он может работать. Кроме того, команда решила по объёму:

- вход анонимно или по логину и паролю;
- мессенджеры не делаем;
- мобильная версия — адаптивный сайт.

## Решение

### Поставщики за адаптерами

Отели, транспорт (авиа и ж/д), трансферы, бронирование и оплата спрятаны за gRPC-контрактами поставщика в `proto/`. У каждого контракта может быть несколько реализаций, конкретная выбирается в конфиге сервиса.

- Сейчас реализации собраны из открытых данных (OSM, открытые датасеты из ADR 0001) с синтетическими ценами и расписаниями поверх.
- Для API Островка или GDS пишется новый адаптер того же контракта; агент, gateway и фронт не меняются.
- В прототипе есть минимум два адаптера одного контракта, чтобы переключение было видно на демо, а не обещано.
- Каждая сущность от поставщика несёт поле `source`: источник, реальные данные или синтетические, ссылка, дата загрузки. Агент и фронт показывают его пользователю.

### Агент как API

Продукт — это агент, а не наш интерфейс.

- Внешний контракт описан в `api/openapi.yaml`: сессии, сообщения, план, корзина, заказы, аккаунт. События хода агента в SSE имеют документированную схему.
- TS-типы фронта генерируются из OpenAPI. Наш React — один из клиентов этого API наравне с любым сторонним.
- Бизнес-правила (политика уточнений, допустимые компромиссы, минимальное время стыковки, наценки) задаются конфигом, а не текстом промпта.

### LLM-провайдер настраивается

Агент работает с любым OpenAI-совместимым эндпоинтом: OpenRouter, свой vLLM, корпоративный шлюз. Адрес, ключ и модели для каждой роли (роутер, основной агент) задаются переменными окружения. Значение по умолчанию — правило из `models.md`: open-weights модели через OpenRouter с `data_collection: deny`. Без ключа агент работает на правилах, и сквозной сценарий проходится.

### Аккаунты

- Анонимный пользователь получает идентификатор в cookie, к нему привязаны чаты, планы, заказы и память.
- Регистрация и вход по логину и паролю. Пароли хешируются argon2id, сессии серверные, идентификатор сессии в cookie `HttpOnly`, `Secure`, `SameSite=Lax`.
- При входе или регистрации все данные анонимного идентификатора переходят в аккаунт.
- Аутентификацию выполняет `gateway`, внутренние сервисы получают идентификатор пользователя в метаданных gRPC.

### Каналы

Только веб, адаптивная вёрстка. Мессенджеры (Telegram, MAX и другие) не делаем совсем. Уведомления и напоминания показываются на сайте.

### Запуск для жюри

- Задеплоенная демо-версия — основной способ проверки.
- Локальный запуск одной командой: готовые образы из публичного GHCR, `.env` генерируется автоматически, данные поставляются снапшотом.
- Профиль compose по умолчанию лёгкий: приложение, PostgreSQL, NATS. Langfuse, ClickHouse, Prometheus и Grafana включаются профилем `full`. Langfuse занимает около 85% памяти всего стека, поэтому без этого разделения ноутбук проверяющего может не потянуть запуск.
- Аналитика и трейсы без профиля `full` выключаются: клиенты ClickHouse и Langfuse уже работают как no-op без адреса и ключей.

## Рассмотренные альтернативы

- **Свои данные прямо в агенте, без контракта поставщика.** Быстрее в первый день, но каждая замена источника затрагивает агента, а бизнесу нечего показать на вопрос «как подключить наш инвентарь».
- **Агент как библиотека внутри нашего фронта или бэкенда.** Проще, но встроить агента в чужой продукт тогда можно только вместе с нашим интерфейсом.
- **Вход только анонимный.** Быстрее, но память между сессиями и «Мои поездки» привязаны к одному браузеру, а это слабо для дополнительной задачи кейса о персонализации.
- **Telegram-бот как второй клиент.** Закрывает пункт кейса о мессенджере, но отнимает время у трека, который отвечает за переиспользуемость. Пункт закрываем мобильной версией.
- **Полный стек по умолчанию.** Один профиль проще поддерживать, но 2,3 ГБ памяти в простое и 7 ГБ образов мешают жюри запустить решение локально.

## Последствия

- Фаза 0 roadmap фиксирует контракты поставщиков, OpenAPI и схему событий раньше, чем начинается работа по трекам; дальше они меняются только через PR, который правит контракт и обе его стороны.
- Появляется код, которого нет в ADR 0001: аккаунты в `gateway`, второй адаптер поставщика, генерация TS-типов, профили compose.
- Поле `source` проходит через все контракты поставщиков; это немного шумнее, зато страница «Откуда данные» собирается из тех же данных, а не пишется руками.
- Решение по моделям и ключам (roadmap, Q-001) меняет только конфиг, не код.
