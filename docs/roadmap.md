# Roadmap

- Срок: неделя до защиты. Основной объём делаем в первые три дня, остаток уходит на доводку.
- Команда: два бэкендера (треки A и B) и фронтендер (трек F). Кто берёт какой трек, команда решает сама.
- Связанные документы: [кейс](case.md), [ADR 0001](adr/0001-architecture.md), [ADR 0002](adr/0002-reusable-agent-platform.md), [модели](models.md).

## Приоритеты

Порядок задан критериями оценки и действует при любом споре о том, что делать первым:

1. **Переиспользуемость реальным бизнесом.** Островок должен суметь подключить решение к своему инвентарю и своему сайту без переписывания агента.
2. **Архитектура.**
3. **Обёртка и внешний вид.**

Отдельная обязанность команды, не связанная с этим порядком: жюри проверяет и запускает решение без усилий.

## Объём

Шесть обязательных задач кейса и все дополнительные: работа после покупки, память между сессиями, метрики качества агента, мобильная версия (адаптивный сайт).

Что решено:

- география: Россия и безвизовые страны, цены в рублях;
- данные: реальные везде, где их можно загрузить, синтетика только поверх них; у каждой сущности записано происхождение, сайт показывает его на карточках и на странице «Откуда данные»;
- агент гибридный (ADR 0002): LLM через вызов инструментов решает, что искать и сравнивать, а изменения плана, инвалидация, стыковки, цены и покупка идут через детерминированный код;
- интерфейс: чат, панель плана и карта, карточки плана правятся руками;
- вход: анонимно или по логину и паролю; при входе анонимные чаты, планы, заказы и память переходят в аккаунт;
- мессенджеры не делаем совсем, ни Telegram, ни другие.

## Сквозные требования

Действуют во всех фазах, а не в одной.

### Переиспользуемость

- Поставщики отелей, билетов, трансферов, бронирования и оплаты стоят за адаптерами с единым gRPC-контрактом. Источник выбирается в конфиге; подключение API Островка или GDS — это новый адаптер, агент при этом не меняется.
- Агент доступен как API (OpenAPI и документированные SSE-события). Наш React — один из его клиентов, не единственный.
- LLM-провайдер — любой OpenAI-совместимый эндпоинт. Модели, адрес и ключ задаются конфигом.
- Бизнес-правила лежат в конфиге, а не в промпте: политика уточнений, допустимые компромиссы, минимальное время стыковки, наценки.
- Метрики в терминах бизнеса с первой фазы: воронка до покупки, средний чек, доля поездок, купленных целиком.

### Удобство проверки

- Запуск одной командой без ключей и без сборки: готовые образы из публичного GHCR, `.env` генерируется сам, данные приезжают снапшотом.
- Лёгкий профиль по умолчанию (приложение, Postgres, NATS). Langfuse, ClickHouse, Prometheus и Grafana включаются профилем `full`.
- Без ключа LLM агент работает на правилах, сквозной сценарий проходится.
- Задеплоенная демо-версия — первая ссылка в README.
- Демо-аккаунт, примеры запросов в интерфейсе, страница «Откуда данные», отчёт eval, который перезапускается одной командой.
- README для проверяющего: что смотреть, сколько это займёт и где закрыт каждый пункт кейса.

## Фаза 0. Контракты

День 1, первая половина. После неё три трека работают параллельно и не ждут друг друга.

| Что | Результат |
|---|---|
| Внешнее API | `api/openapi.yaml`: сессии, сообщения, SSE-события, план, корзина, заказы, аккаунт; TS-типы фронта генерируются из него |
| TripPlan v2 | Поездка из компонентов: транспорт туда и обратно (авиа или ж/д), проживание, трансферы. У каждого варианта объяснение, компромиссы и риски. Стыковки и конфликты. Одна схема для агента, фронта и eval |
| Внутреннее API | proto v2 поставщиков: направления, отели, транспорт, трансферы; booking с корзиной из нескольких позиций |
| Происхождение данных | Общее поле `source` во всех сущностях: источник, реальные или синтетические данные, ссылка, дата загрузки |
| Конфиг | Адаптеры поставщиков, LLM-провайдер, бизнес-правила |
| Моки | Фронт работает от моков по OpenAPI |

После фазы 0 контракт меняется только через PR, который правит одновременно `openapi.yaml` или `.proto` и код по обе стороны.

Готово, когда: фронт собирается на сгенерированных типах и показывает план из мока; бэкенд компилируется против proto v2.

## Фаза 1. Сквозной путь по обязательным задачам

Дни 1–3.

**Трек A, агент:**

- гибридный цикл вызова инструментов поверх TripPlan v2;
- уточняет только то, без чего нельзя двигаться дальше, остальное заполняет видимыми допущениями;
- вдохновение: направления с ценой, погодой и временем в пути;
- сравнение по важному для пользователя: отмена, питание, расположение, время в пути;
- объяснение выбора: почему вариант подходит, чем пришлось пожертвовать, какие риски;
- проверка стыковок: прилёт, заселение, трансфер;
- пересборка плана через инвалидацию, без поиска с нуля.

**Трек B, данные и сервисы:**

- загрузка реальных данных по источникам из ADR 0001: отели и точки интереса из OSM, аэропорты и маршруты, ж/д станции, каталог направлений, погода;
- синтетические цены и расписания поверх реальных объектов;
- адаптеры поставщиков по proto v2;
- корзина и имитация оплаты в booking;
- метрики воронки в ClickHouse;
- лёгкий профиль compose и `run.sh`.

**Трек F, интерфейс:**

- чат и панель плана с таймлайном поездки;
- таблица сравнения вариантов;
- ручная правка карточек (даты, гости, бюджет) через тот же механизм пересборки, что и текстовые сообщения;
- корзина и экран оплаты;
- пометки об источнике данных и страница «Откуда данные»;
- адаптивная вёрстка с первого дня.

Готово, когда: на задеплоенном сервере запрос «хочу к тёплому морю в ноябре, недорого, с ребёнком, без долгих перелётов» доходит до оплаченной корзины с транспортом, отелем и трансфером; изменение «а если на два дня позже» пересобирает план без нового выбора направления.

## Фаза 2. Аккаунты, память, работа после покупки, eval

Дни 3–5.

| Трек | Что |
|---|---|
| A | Память между сессиями: агент записывает предпочтения в профиль и учитывает их в новых поездках. Eval: около 50 тестовых запросов, автопрогон одной командой, метрики кейса (доля доведённых до конца сценариев, число уточнений, время до первой рекомендации, ошибки в стыковках) |
| B | Регистрация и вход по логину и паролю, перенос анонимных данных в аккаунт. Работа после покупки: смена дат с пересчётом цены, запрос раннего заезда, трансфер к купленному отелю, напоминания. Второй адаптер поставщика для демонстрации переключения |
| F | Вход и регистрация, «Мои поездки», страница заказа с действиями после покупки, уведомления на сайте, страница метрик агента |

Готово, когда: анонимный пользователь собирает поездку, регистрируется перед оплатой и видит её в «Моих поездках»; во второй сессии агент учитывает предпочтения из первой; eval выдаёт отчёт по всем четырём метрикам.

## Фаза 3. Доводка под жюри

Дни 5–7.

- Eval на свежих запросах, которых команда не видела; правки промптов и инструментов по провалам.
- Деградация: если LLM или внешний источник недоступен, работают запасные пути.
- Лимит расходов на LLM и защита от злоупотреблений.
- Снапшот данных в релизе, README для проверяющего, сценарий демо.
- Карта, анимации и шлифовка визуала по остатку времени.
- Заморозка деплоя за день до защиты.

## Открытые вопросы

- **Q-001.** Внешние модели и ключи: организаторы ответят в понедельник, 2026-10-26. До ответа провайдер остаётся настраиваемым, значение по умолчанию — правило из `models.md` (open-weights через OpenRouter).
- **Q-002.** Реальные цены на билеты по России и безвизовым направлениям: трек B в первый день проверяет, откуда их можно брать. Где не выйдет — синтетика с пометкой.
