## Приоритеты

Порядок задан критериями оценки и действует при любом споре о том, что делать первым:

1. **Переиспользуемость реальным бизнесом.** Островок должен суметь подключить решение к своему инвентарю и своему сайту без переписывания агента.
2. **Архитектура.**
3. **Обёртка и внешний вид.**

Отдельная обязанность команды, не связанная с этим порядком: жюри проверяет и запускает решение без усилий.

Организаторы на Q&A подтвердили тот же порядок: переиспользуемость в реальном бизнесе, затем архитектура, затем обёртка (вопрос 34).

## Что поменял Q&A 2026-10-25

- Сдача на два дня раньше, чем выходило по «неделе»: фазы 2 и 3 сжаты до одного дня каждая (2026-10-26 фаза 3 разделена на eval и доводку, см. выше).
- Отели первичны, перелёты и трансферы — дополнение. Транспорт и трансферы остаются в объёме фазы 1 и дальше не расширяются; глубина идёт в отели.
- Синтетические цены допустимы с пометкой «демо», в том числе в ответе агента.
- Жюри запускает решения у себя, незапустившееся уходит вниз списка: проверка запуска из чистого клона — обязательный шаг перед сдачей.
- Скрейпинг не делаем (`spec.md`, Q-004 решён).
- Ключи LLM: работаем через внешний API-ключ, локальную модель не поднимаем; как ключ попадёт к жюри — ответ организаторов (Q-001).
- Промпт-инъекции — дисквалификация: в репозитории нет текста, адресованного проверяющим; агент защищён от инъекций во вводе пользователя.
- На защите финалистов спрашивают по логике кода: каждая роль объясняет свою зону.
- География остаётся широкой по ADR 0003, хотя организаторам хватает одной локации.

## Объём

Шесть обязательных задач кейса и все дополнительные: работа после покупки, память между сессиями, метрики качества агента, мобильная версия (адаптивный сайт).

Что решено:

- география: Россия и все страны с пометкой визы по гражданству путешественника, подбор по умолчанию безвизовый, цены в рублях (ADR 0003; до 2026-10-25 было «Россия и безвизовые страны»);
- данные: реальные везде, где их можно загрузить, синтетика только поверх них; у каждой сущности записано происхождение, сайт показывает его на карточках и на странице «Откуда данные»;
- агент гибридный (ADR 0002): LLM через вызов инструментов решает, что искать и сравнивать, а изменения плана, инвалидация, стыковки, цены и покупка идут через детерминированный код;
- интерфейс: чат, панель плана и карта, карточки плана правятся руками;
- вход: анонимно или по логину и паролю; при входе анонимные чаты, планы, заказы и память переходят в аккаунт;
- мессенджеры не делаем совсем, ни Telegram, ни другие.

## Сквозные требования

Действуют во всех фазах, а не в одной.

### Переиспользуемость

- Поставщики отелей, билетов, трансферов, бронирования и оплаты стоят за адаптерами с единым gRPC-контрактом. Источник выбирается в конфиге; подключение API Островка или GDS — это новый адаптер, агент при этом не меняется.
- Агент доступен как API (OpenAPI и документированные SSE-события). Наш React — один из его клиентов, не единственный.
- LLM-провайдер — любой OpenAI-совместимый эндпоинт. Модели, адрес и ключ задаются конфигом.
- Бизнес-правила лежат в конфиге, а не в промпте: политика уточнений, допустимые компромиссы, минимальное время стыковки, наценки.
- Метрики в терминах бизнеса с первой фазы: воронка до покупки, средний чек, доля поездок, купленных целиком.

### Удобство проверки

- Запуск одной командой без ключей и без сборки: готовые образы из публичного GHCR, `.env` генерируется сам, данные приезжают снапшотом.
- Лёгкий профиль по умолчанию (приложение, Postgres, NATS). Langfuse, ClickHouse, Prometheus и Grafana включаются профилем `full`.
- Без ключа LLM агент работает на правилах, сквозной сценарий проходится.
- Задеплоенная демо-версия — ссылка в README рядом с инструкцией запуска; основной путь проверки — локальный запуск.
- Демо-видео своим голосом, ссылкой в README, доступ проверен из анонимного окна.
- Перед сдачей — запуск из чистого клона по README на машине, где решение ещё не запускали.
- Демо-аккаунт, примеры запросов в интерфейсе, страница «Откуда данные», отчёт eval, который перезапускается одной командой.
- README для проверяющего: что смотреть, сколько это займёт и где закрыт каждый пункт кейса.

## Фаза 0. Контракты

2026-10-25, закрыта PR #1. После неё три трека работают параллельно и не ждут друг друга.

| Что | Результат |
|---|---|
| Внешнее API | `api/openapi.yaml`: сессии, сообщения, SSE-события, план, корзина, заказы, аккаунт; TS-типы фронта генерируются из него |
| TripPlan v2 | Поездка из компонентов: транспорт туда и обратно (авиа или ж/д), проживание, трансферы. У каждого варианта объяснение, компромиссы и риски. Стыковки и конфликты. Одна схема для агента, фронта и eval |
| Внутреннее API | proto v2 поставщиков: направления, отели, транспорт, трансферы; booking с корзиной из нескольких позиций |
| Происхождение данных | Общее поле `source` во всех сущностях: источник, реальные или синтетические данные, ссылка, дата загрузки |
| Конфиг | Адаптеры поставщиков, LLM-провайдер, бизнес-правила |
| Моки | Фронт работает от моков по OpenAPI |

После фазы 0 контракт меняется только через PR, который правит одновременно `openapi.yaml` или `.proto` и код по обе стороны.

Готово, когда: фронт собирается на сгенерированных типах и показывает план из мока; бэкенд компилируется против proto v2.

## Фаза 1. Сквозной путь по обязательным задачам

2026-10-25 — 2026-10-26; для DS и FE — до 2026-10-27, 12:00. Бэкенд (`P1-BE-01…13`) смержен и задеплоен 2026-10-26, подключение настоящих данных — по мере мержа наборов DS. Цель, точки стыковки и риски — [спека 0003](specs/0003-phase1-plan.md); задачи по ролям с подзадачами и зависимостями — [docs/phase1](phase1/README.md): [бэкенд](phase1/backend.md), [данные](phase1/data.md), [фронт](phase1/frontend.md).

**Этап 1.0, день 1, первая половина: контракт виз и гражданства.** Один PR бэкенда и фронта по [спеке 0002](specs/0002-visa-and-citizenship.md): гражданство в плане, визовый статус у направлений, справочники стран и городов. Идёт первым, потому что от него зависят задачи всех ролей.

**BE, бэкенд:**

- загрузка снапшота данных в `inventory`;
- провайдеры поверх данных: `catalog` (направления, визы, страны, города отправления, погода), `lodging` на отелях OSM, `transport` (авиа и ж/д), `transfer`;
- гибридный цикл вызова инструментов поверх TripPlan v2: вдохновение, сравнение, объяснение выбора;
- сборка полной поездки и валидатор стыковок, включая визовые проверки;
- пересборка плана через инвалидацию, без поиска с нуля;
- справочники и «Откуда данные» в gateway, метрики воронки в ClickHouse, лёгкий профиль compose и `run.sh`.

**DS, данные:**

- каркас `data/`: загрузчики, снапшот, валидатор, реестр источников;
- страны и визовая матрица по всем паспортам, сверка для граждан России со справкой МИД;
- курируемый каталог направлений с климатом, города и аэропорты, отели OSM, маршруты и ж/д;
- калибровка синтетических цен, курсы ЦБ, туристический налог.

**FE, фронт:**

- каркас, токены дизайн-системы, адаптивная вёрстка с первого дня;
- выбор гражданства и города отправления, вдохновение с визовыми пометками;
- таймлайн поездки, таблица сравнения, ручная правка карточек через тот же механизм пересборки, что и текстовые сообщения;
- корзина и экран оплаты;
- пометки об источнике данных и страница «Откуда данные».

Готово, когда: на задеплоенном сервере запрос «хочу к тёплому морю в ноябре, недорого, с ребёнком, без долгих перелётов» доходит до оплаченной корзины с транспортом, отелем и трансфером; изменение «а если на два дня позже» пересобирает план без нового выбора направления; для гражданина Беларуси подбор и визовые пометки считаются по его паспорту.

## Открытые вопросы

- **Q-001.** Как ключ LLM попадёт к жюри: организаторы ответят 2026-10-26. Решено командой: внешний API-ключ, без локальной модели, значение по умолчанию — правило из `models.md` (open-weights через OpenRouter).
