## Правила зависимостей

1. **Подзадача выполнена, когда её PR смержен в `main`.** Не «почти готово в ветке» и не «работает у меня» — только мерж.
2. **Зависимость бывает двух видов:**
   - **блокирующая** — начинать нельзя, пока зависимость не смержена;
   - **на подключение** — начинать можно сразу на заглушке (моки, тестовый снапшот, файл по формату из спеки), а после мержа зависимости остаётся короткая подзадача «подключить настоящее».
3. **Межролевая блокирующая зависимость в фазе 1 одна:** подзадачи фронта `P1-FE-01.1` и `P1-FE-01.2` ждут контракт виз `P1-BE-01` (таблица ниже). Всё остальное между ролями — на подключение.
4. **Внутри роли** порядок подзадач задаёт сам исполнитель, но указанные зависимости соблюдаются.
5. **Если нужна новая зависимость**, которой здесь нет (например, фронту не хватает поля в API), — это изменение контракта: PR в `api/openapi.yaml` или `proto/`, который правит обе стороны (roadmap, правило после фазы 0). Не договариваемся в чате, не ждём молча.

Нумерация: `P1-<роль>-<задача>.<подзадача>`, например `P1-BE-03.2`. Номера не переиспользуются.

## Общие правила PR

- Одна подзадача или несколько связанных подзадач одной роли — один PR в `main`.
- В каждом PR — запись в `CHANGELOG.md` с хешем коммита (README, «Журнал изменений»).
- Мерж только через «Create a merge commit»: squash и rebase меняют хеши.
- Контракт (`api/openapi.yaml`, `proto/`) меняется PR, который правит обе стороны; ревью — синхронное, с той ролью, которую он задевает.
